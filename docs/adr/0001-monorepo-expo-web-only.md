# 0001. Монорепо на шаблонах пользователя, сайт — только Expo web

## Контекст

Пользователь дал шаблоны фронта (Expo-MVVM-Template, Expo 54) и бэка (nest-template: NestJS + TypeORM + PostgreSQL). Заказан сайт, мобильное приложение не заказано. Тот же стек уже собирался в TicketService и AdAuction.

## Решение

Один репозиторий `E:\KlgSynagogue`: `backend/` — nest-template как есть, `frontend/` — Expo-MVVM-Template. Единственная цель сборки фронта — Expo web в режиме SPA (`web.output: "single"`, без SSR). Всё, что завязано на DOM (scroll-эффекты, прелоадер, сцена, kit), пишется как web-реализация (`*.web.tsx`, DOM + CSS-переменные). На нативе остаётся простой статичный фолбэк. Модули шаблона, которые не нужны (Redis, очереди, почта, i18n бэка, file-storage), не подключаются и исключены из lint.

## Почему

- **Next.js / Astro (SSR/SSG)** для контентного сайта подходят лучше по SEO и первой загрузке. Отвергнуто, потому что пользователь явно задал шаблон фронта, а уход от него ломает требование и лишает проект готовых решений из прошлых сборок (MVVM, RTK Query, i18next).
- **Полноценный кроссплатформенный UI** (react-native-компоненты без DOM). Отвергнуто: scroll-хореография эталона halalcash сделана на CSS-переменных и `position: sticky`, а в RN её пришлось бы писать заново и хуже. Приложение при этом никто не заказывал.
- **Два отдельных репозитория** отвергнуты: контракт API меняется вместе с экранами, а смоуки поднимают бэк и фронт вместе.

## Последствия

- SPA без пререндера: поисковики видят пустой HTML, первая загрузка тяжелее. Если SEO станет важным, нужен пререндер или SSR, а это уже переезд, не настройка.
- Нативная сборка формально есть, но там лишь заглушка. «Выпустить приложение» потребует отдельного UI.
- Неподключённые модули шаблона лежат в дереве `backend/src/shared/*` мёртвым кодом. Трогать их нельзя: шаблон должен обновляться без конфликтов.
