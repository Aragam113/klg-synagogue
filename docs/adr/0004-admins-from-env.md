# 0004. Админы из env, без таблицы пользователей

## Контекст

Пользователь попросил «админку на сайте». Редакторов один-два. Входа для прихожан нет (личный кабинет вне рамок), почтового сервиса тоже нет. В TicketService так же сделано в ADR 0004.

## Решение

Учётки редакторов задаются переменной `ADMIN_USERS` в виде списка `email:bcrypt-hash`. Хеш делает `npm run admin:hash -- <пароль>`. `POST /admin/login` выдаёт JWT. Все `/admin/*` закрыты `AdminGuard`. Таблицы пользователей, ролей, регистрации и сброса пароля нет.

## Почему

- **Таблица `users` с ролями и экраном управления.** Отвергнуто: при двух редакторах это лишние миграции, CRUD, сброс пароля (а почты нет) и лишняя поверхность для атак. Всё это ради сценария, которого пока нет.
- **Внешний провайдер входа** (OAuth Google/Яндекс, Telegram Login). Отвергнуто: зависимость от внешнего сервиса, настройка приложения у провайдера и привязка к чужим аккаунтам. Редакторов от этого больше не станет.
- **HTTP Basic на уровне веб-сервера.** Отвергнуто: нельзя отличить «истёк вход» от «нет прав», фронту нужен свой экран логина с редиректом обратно, а деплой пока не определён.

## Последствия

- Чтобы добавить или убрать редактора, надо править env и перезапускать бэк. Через интерфейс это не делается.
- Ролей нет: каждый редактор видит всё, включая платежи, заявки с ПДн и подписчиков.
- Нет аудита «кто что изменил», а заметки к заявкам анонимны.
- Отозвать конкретный выданный JWT нельзя. Остаётся только сменить секрет, и тогда разлогинятся все.
- Если появится потребность в ролях или в личном кабинете прихожан, нужна таблица пользователей и миграция. Это решение придётся отменить.
